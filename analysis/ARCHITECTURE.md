# Parakeet TDT 0.6B v3 on the GTX 750 Ti: first architecture pass

Analysis date: 2026-10-01. This is an inventory and design analysis, not a
measured CUDA speedup. The inspected runtime source is NVIDIA/NeMo-Speech.cpp
commit `4c101bc`; the installed CPU binary is release `v0.1.0`. The model is
NVIDIA's `parakeet-tdt-0.6b-v3.q8_0.gguf` with SHA-256
`e3880d0aaaaf2c308ea2c35016b2b895c423eb3fda924c1b463d1c19b7f4d32e`.
The exact GGUF inventory is in `gguf_inventory.txt`, generated by
`inspect_gguf.py` without loading the weights. The source reference is the
local `../nemo-speech-src` checkout, primarily
`src/asr/encoder/fastconformer.cpp`, `rel_pos_attention.cpp`,
`src/asr/decoders/rnnt_modules.cpp`, and `rnnt_greedy_decoder.cpp`.

## Actual machine and control workload

The GTX 750 Ti is Maxwell `sm_50`, with no Tensor Cores, DP4A, or useful native
FP16/BF16 matrix arithmetic. NVIDIA's reference specifications give 640 CUDA
cores and 86.4 GB/s peak memory bandwidth. CUDA 12.9 can compile `sm_50`;
CUDA 13 cannot. The local toolkit is CUDA 12.9.86, and the driver is 580.173.02.
An elevated `nvidia-smi` probe reported 2048 MiB total, 950 MiB used, and
1041 MiB free; a later probe showed 1053 MiB free and PCIe generation 3 ×16.
Retaining the CUDA primary context and calling `cuMemGetInfo` showed 1040.0
MiB free, so context creation alone did not consume much of the available
memory. A later probe saw 1182.5 MiB free and successfully reserved and
immediately released a 681 MiB CUDA allocation, leaving 501.5 MiB free while
reserved. This verifies that a model-sized weight allocation fits at that
moment; it does not validate the full runtime's scratch and library needs.
Free VRAM changes with desktop activity. The ordinary agent sandbox
hides the GPU device nodes, so CUDA execution requires elevated access.
System RAM is 15 GiB, with about 6 GiB available when inspected; retaining
the 681 MiB GGUF in RAM is practical.

`short-speech.mp3` is 35.304 seconds. The current CPU
wrapper transcribed it in three uncontrolled one-shot runs of 16.05, 12.20,
and 14.12 seconds; peak process RSS was about 949–954 MiB. These include model
loading, MP3 conversion, and decoding. They are a practical end-to-end target,
not steady-state kernel timings. The 12.20-second run had the model in the OS
page cache and enabled memory diagnostics.

## Exact model structure

1. **Frontend.** Input is 16 kHz mono audio. A 512-point STFT uses a 25 ms
   window, 10 ms hop, 128 mel bins, pre-emphasis 0.97, and utterance-level
   per-feature normalization. The model carries its mel filterbank. The
   preprocessor outputs roughly 100 mel frames per second. Its normalization
   requires statistics over the utterance; independent short chunks would not
   have exactly the same input values. The upstream GPU frontend implements the
   STFT as two dense real/imag DFT matrix multiplies because ggml has no FFT;
   its CPU path uses a radix-2 FFT. On Maxwell, computing mel on the CPU and
   uploading about 1.7 MiB of features for this clip may beat the GPU DFT
   path and avoid extra GPU workspace. This needs measurement.
2. **Subsampling stem.** Three stride-2 convolution stages reduce time by 8
   and mel frequency from 128 to 16. The first is a 3×3 convolution from one
   input channel to 256 channels, followed by two groups of 3×3 depthwise
   convolution, 1×1 pointwise convolution, and ReLU. The 256×16=4096 features
   at each output time are projected to the 1024-wide encoder. The three 3×3
   stride-2 convolutions have a 15-mel-frame temporal receptive field, which
   makes exact, haloed stem chunking possible in principle. For this clip,
   the encoder sequence is roughly 441 frames, each about 80 ms of audio.
3. **Encoder.** Twenty-four FastConformer blocks, width 1024, 8 attention heads
   of width 128, feed-forward width 4096, and depthwise temporal kernel 9.
   Each block applies LayerNorm, a 1024→4096→1024 SiLU feed-forward branch
   with residual factor 0.5; LayerNorm and bidirectional relative-position
   attention with a residual; LayerNorm and a convolution branch with a
   residual; a second factor-0.5 feed-forward branch; and final LayerNorm.
   The convolution branch is 1024→2048 pointwise, GLU, width-9 depthwise,
   batch norm, SiLU, and 1024→1024 pointwise. Attention uses Q/K/V and output
   projections, plus a per-layer positional projection and learned `u/v`
   biases. The GGUF declares unrestricted offline left/right context and no
   cache-aware streaming. This is full-utterance bidirectional inference.
4. **TDT head.** The encoder output is projected from 1024 to a 640-wide joint
   space. The predictor embeds the previous token at width 640 and passes it
   through two 640-wide LSTM layers; its output is separately projected to
   width 640. The joint adds the encoder and predictor projections, applies
   ReLU, then projects to 8198 logits: 8193 token choices (8192 vocabulary
   entries plus blank token 8192) and 5 duration choices `[0,1,2,3,4]`.
   Greedy decoding chooses token and duration, advances 0–4 encoder frames,
   and allows up to 10 symbols per frame. It is sequential in emitted tokens.

The positional tensor holds 9999 positions ×1024 F32 values; it accounts for
39.06 MiB. The model's maximum positional length is 5000 encoder frames,
roughly 400 seconds at 80 ms/frame. Beyond ordinary short clips, attention's
quadratic scratch and time become a separate concern.

## Weights and VRAM

The GGUF has 701 tensors and 713,975,456 file bytes. Tensor payloads are
680.74 MiB, with a small header/alignment remainder. The payload breakdown:

| Payload | MiB | Important detail |
| --- | ---: | --- |
| Q8_0 tensors | 629.29 | 32 signed 8-bit values plus one FP16 scale per block (34 bytes/32 values) |
| F32 tensors | 40.77 | Mostly the 39.06 MiB positional table |
| F16 tensors | 10.69 | Mostly the 10.00 MiB token embedding |

By component, the four feed-forward matrices in every block occupy 408.00
MiB, or 59.9% of payload. Attention weights occupy 127.69 MiB; convolution
weights and batch-norm parameters 77.30 MiB. Each 1024×4096 Q8 feed-forward
matrix is 4.25 MiB. The 24 encoder blocks dominate both storage and dense
compute. Expanding all Q8 weights to F32 would require about 2.46 GiB just
for those weights and is impossible here. The original Q8 representation
should remain the long-lived storage format.

The installed CPU runtime reported 658.17 MiB in its encoder model container
and 22.80 MiB in the decoder container. On this 35-second input it reported
a 234.28 MiB CPU scheduler compute buffer; this is **not** a measured CUDA
allocation. An earlier warmup shape used 26.77 MiB. The graph's sum of tensor
view sizes exceeds 9 GiB but is not the physical allocation: ggml reuses
buffers. The large stem intermediates are revealing: a first-stage output
view is about 110 MiB and a later 3×3 im2col buffer is about 124 MiB. A
direct depthwise convolution or a correctly haloed chunked stem could remove
much of the im2col/stem peak without changing full-context encoder math.

At the observed 1041 MiB free, subtracting 681 MiB model storage and a
234 MiB buffer of similar size leaves only 126 MiB for a CUDA context,
frontend scratch, library workspace, and other allocations. The GPU compute
buffer may be different from the CPU one, so actual CUDA load and peak VRAM
must be measured. Keeping every weight resident is plausible but unsafe to
assume. The model's offline architecture permits layer-by-layer weight
streaming if residency fails; a block's weights are only about 27 MiB and the
measured PCIe link is gen 3 ×16. Transfer cost must be measured, not inferred
from nominal PCIe bandwidth.

### Full residency versus layer streaming

The model is a chain: block 0 produces a `[1024,T]` activation for block 1,
and so on through block 23. The small positional slice is reused by every
block. A block has no dependency on another block's weights once its output is
computed. Thus, keeping the GGUF backed by system RAM, uploading one or a few
blocks' roughly 27 MiB of weights, executing them, reusing that device slot
for later blocks, and finally running the TDT head preserves the architecture.
The activation stays on the GPU. Two slots can prefetch the next block while
the current block runs. The host needs only one model copy plus small pinned
staging buffers; the GPU needs those one/two block slots and a reusable
activation/scratch arena. The current NVIDIA runtime does **not** provide this
layer-streaming mode: its tensor container places all model weights into the
first accelerator's persistent allocation during `Session::setup()`.

For the current 35-second clip, a full-resident build might work after reducing
scratch. The 124 MiB im2col buffer is a promising target. Running the FFT
frontend and serial decoder on the CPU would also avoid their GPU resources;
keeping only the needed positional slice rather than the full 39 MiB table
could save roughly 35 MiB. These are design estimates. If the complete CUDA
runtime fits with a comfortable measured margin under normal desktop load,
full residency avoids repeated PCIe weight copies. If it remains near the
limit or fails, layer streaming is the robust path. It is a runtime refactor,
not a small change to one GEMM kernel.

The 234 MiB diagnostic is **one high-water compute pool**, not 234 MiB for
each of 24 layers. ggml allocates temporary operation results in this pool
and reuses regions after their last consumer. It includes large stem outputs
and im2col staging as well as later encoder intermediates. Weights are
separate persistent allocations. The reported 9 GiB sum of graph tensor
sizes counts views and overlapping lifetimes, so it cannot be added to VRAM.

## Compute and kernel implications

For a roughly 441-frame encoder sequence, the dense projection shapes are
`[1024,4096] × [4096,441]` and its reverse for four feed-forward GEMMs per
block; `[1024,1024] × [1024,441]` for attention Q/K/V/output and convolution
pointwise work; and `[1024,1024] × [1024,881]` for each relative-position
projection. A rough multiply-add count is over 0.5 trillion FP32-equivalent
operations for the full encoder, dominated by the two feed-forward branches.
This is a shape estimate, not a profiler result.

`sm_50` lacks int8 matrix dot instructions and Tensor Cores. A viable GEMM
must either dequantize Q8 weights inside an FP32 tiled kernel, or dequantize
one matrix at a time to an approximately 16 MiB F32 scratch matrix and call
cuBLAS SGEMM. Both keep the persistent weight copy compact. Their actual
speed and scratch cost need paired measurement. NVIDIA's patched
`skinny-q8` kernel in this source requires Ampere int8 MMA and `cp.async`;
its wide planar-Q8 path explicitly rejects older GPUs. The on-disk GGUF uses
portable `block_q8_0`, which a Maxwell kernel can consume or repack into a
single compact in-memory layout. Never keep both full-model layouts in VRAM.

Relative-position attention performs QK scores, a second Q×position term,
relative shift, softmax, and weighted V. One ordinary F32 score matrix at
441 frames and 8 heads is about 5.9 MiB; at 2250 frames (three minutes of
audio) it becomes about 154 MiB. Fused or tiled attention can avoid storing
the full score and relative-shift intermediates, but the 35-second control
clip makes the stem and dense projections the stronger first targets.

The TDT decoder is a small serial tail. The current runtime already splits
encoder and predictor/joint sessions. Keeping the 22.8 MiB decoder on CPU is
worth evaluating: transfer of the 640×441 encoder projection is about 1.1
MiB, and avoiding repeated GPU-to-host token synchronizations may help. It
must be measured against a fully GPU decoder.

## Experiment order

1. Build a minimal NVIDIA CUDA ASR runtime from source for `sm_50` with CUDA
   12.9 and the existing block-Q8 GGUF. The published Linux CUDA release is
   documented for Turing-class GPUs and newer. Check actual model load,
   allocation sizes, backend coverage, output parity, and end-to-end time on
   `short-speech.mp3` before changing kernels.
2. Make the model fit reliably under the live free-VRAM limit. Try CPU mel
   frontend and CPU TDT decoder, skip unnecessary warmup, then replace the
   stem's large im2col/depthwise path with a direct or chunked implementation.
   Treat full-utterance mel normalization and stem halo alignment as part of
   correctness.
3. Benchmark two Maxwell dense controls at the real shapes: direct Q8×F32
   tiled GEMM and per-matrix Q8→F32 plus cuBLAS SGEMM. Start with the four
   feed-forward matrices because they dominate model bytes and arithmetic.
   Optimize only after fixed numerical and transcript checks pass.
4. Profile attention and the TDT tail on the working GPU runtime. Try compact
   attention only when its measured share or longer-audio memory warrants it.
   If full residency still fails, stream one encoder layer's Q8 weights at a
   time and compare transfer-plus-compute against the resident design.
